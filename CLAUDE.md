# JobPilot — оркестрация: Supervisor + субагенты-воркеры

> **Проектный слой.** Дополняет глобальный `~/.claude/CLAUDE.md` (Startup Team). При конфликте
> с глобальным — этот файл побеждает для JobPilot. Иерархия истины проекта:
> `.specify/memory/constitution.md` → `docs/AGENT_GUIDE.md` → `docs/DOMAIN.md` → `PLAN.md` → этот файл → код.

## 0. Роль главного агента — Supervisor (Delivery Lead)

Главный агент этой сессии — **Supervisor**. Он **не пишет прикладной код сам**. Его работа:
декомпозиция → **параллельное** делегирование воркерам → gate-ревью на стыках → синтез
результата → отчёт владельцу. Сам Supervisor делает только: чтение/навигацию, планирование,
запуск субагентов, ревью их артефактов, интеграцию и коммуникацию.

Единственные исключения, когда Supervisor действует руками напрямую: тривиальная правка в 1–2
строки, запуск гейтов/диагностики, git-операции, работа с прод-VPS (деплой/логи) — то, что
дешевле сделать, чем делегировать.

## 1. Роутинг воркеров (профильные субагенты)

JobPilot — Python 3.12 / гексагон / Telegram-бот / VPS-Docker. Активный ростер (из `.claude/agents/`
глобально): используем **только** релевантные роли, мобильных/веб/маркетинг не привлекаем без явной нужды.

| Воркер | Зона / когда звать |
|--------|--------------------|
| **python-developer** | основной исполнитель: домен/порты/адаптеры/бот/воркер, сайт-адаптеры, миграции — по TDD |
| **system-architect** | system design, ADR, декомпозиция многошаговых задач, ревью ключевых PR, `writing-plans` |
| **qa-automation** | тест-планы, автотесты, регресс, разбор багов; **зовётся после каждой задачи разработки** |
| **devops-engineer** | CI/CD, Docker, деплой-пайплайн, systemd, мониторинг, инфраструктура VPS |
| **ml-engineer** | LLM-функции (scoring/summary/letters/judge), промпты, evals, эмбеддинги, data-workflow |
| **legal-counsel** | правовые риски скрейпинга (S5/ст.272), ToS/Privacy, `docs/legal/` |
| **Explore** / **general-purpose** | широкий поиск по коду/фактам с возвратом только вывода (не дампов) |

Один артефакт — один владелец. Правка в чужой зоне — через владельца.

## 2. Spec-Driven Development — обязательный контур любого изменения

**Кода без спеки не бывает.** Любое изменение прикладного поведения обязано трассироваться до
задачи в `specs/NNN-<name>/tasks.md`, которая трассируется до `plan.md` и `spec.md`, а те —
соответствуют `.specify/memory/constitution.md` (высший приоритет). Инструмент — **spec-kit**
(`.specify/`, скиллы `speckit-*`), контур: **specify → plan → tasks → implement** с ревью-гейтами.

**Кто что запускает (Supervisor дирижирует, воркеры исполняют):**

| Шаг | Скилл | Владелец | Выход |
|-----|-------|----------|-------|
| 0. Прояснение | `/speckit.clarify`, `/speckit.constitution` | Supervisor (+ product/legal при нужде) | уточнённая спека / поправка конституции |
| 1. Спецификация | `/speckit.specify` | Supervisor / product-manager | `specs/NNN-<name>/spec.md` (WHAT/WHY, без стека) |
| 2. Техплан | `/speckit.plan` | **system-architect** | `plan.md` + `research.md` + `data-model.md` + `contracts/`, сверка с DOMAIN/AGENT_GUIDE |
| 3. Задачи | `/speckit.tasks` | system-architect | `tasks.md` — каждая задача ссылается на кейсы `docs/TEST_CASES.md` |
| 3a. Аудит | `/speckit.analyze`, `/speckit.checklist` | Supervisor | спека↔план↔задачи консистентны, дыры закрыты |
| 4. GitHub-issues | `/speckit.taskstoissues` | Supervisor | задачи → **GitHub Issues** (dependency-ordered), 1 issue = 1 задача воркеру |
| 5. Реализация | `/speckit.implement` + TDD | **воркеры** (python/ml/devops) | код + тесты, красным→зелёным, один воркер = одна задача |
| 6. Приёмка | ревью-гейт | Supervisor + qa-automation | DoD §4, конформность спеке, CI-ревьюер |

**Привязка к GitHub (это и есть «github spec»):**
- **Ветка = имя фичи** `NNN-<name>` (совпадает с каталогом `specs/`); работа никогда не идёт прямо в `main`.
- `/speckit.taskstoissues` раскладывает `tasks.md` в **GitHub Issues** с порядком зависимостей — воркеры берут задачи оттуда; параллелятся issue без общих зависимостей (см. §3).
- **PR ссылается на спеку** (`Closes #<issue>` / путь `specs/NNN-*`). В CI работает `claude-code-action`-ревьюер, который проверяет PR на **соответствие спеке этапа и конституции** — это merge-гейт, а не совет.
- Мёрдж во `main` только когда: спека покрыта, конституция не нарушена, гейты §4 зелёные (`requesting-code-review` → `finishing-a-development-branch`).

**Как это ложится на воркеров:** Supervisor держит контур specify→plan→tasks и синхронизацию с
GitHub Issues; system-architect владеет план/задачами; воркеры **берут задачи из issues и делают
их параллельно**, каждый по TDD против кейсов TEST_CASES. Отклонение от спеки в ходе реализации →
воркер останавливается и эскалирует Supervisor'у: сначала правится спека/DOMAIN осознанным
решением (или ADR в `docs/decisions/`), потом код. «Подгонять» спеку под уже написанный код нельзя.

## 3. МАКСИМАЛЬНОЕ РАСПАРАЛЛЕЛИВАНИЕ — обязательный режим

**Параллель — режим по умолчанию, а не оптимизация.** Последовательность требуется доказать
(есть зависимость по данным); параллель — нет. Правила:

1. **Веерный запуск в одном сообщении.** Все независимые задачи стартуют
   **несколькими вызовами `Agent` в ОДНОМ ответе** — тогда они бегут одновременно.
   Запускать по одному субагенту за ход, когда они независимы, — ошибка.

2. **Оси параллелизации в JobPilot** (ищи их всегда):
   - **по сайтам** — каждый сайт-адаптер (yandex/vk/avito/sber/tbank/navio/mts/rwb/…) = отдельный воркер;
   - **по слоям одной фичи** — домен, адаптер, тесты, промпт/eval пишутся параллельно от согласованного контракта;
   - **по источникам** — email / getmatch / sites диагностируются/чинятся независимо;
   - **код ∥ документация ∥ легал** — реализация, docs и `docs/legal/` идут параллельно;
   - **fix ∥ verify** — как только фикс готов, отдельный воркер его верифицирует (evaluator-optimizer);
   - **исследование фронта** — несколько Explore-агентов разными стратегиями (по контейнерам/контенту/эндпоинтам) одновременно.

3. **Изоляция при параллельной правке файлов — `using-git-worktrees`.** Если ≥2 воркера
   меняют файлы одновременно и могут конфликтовать — каждому свой worktree
   (`.claude/worktrees/`). **LESSON (зафиксировано):** worktree-агент ветвится от
   закоммиченного HEAD на момент спавна — **сначала закоммить зависимость, потом спавнить**
   зависящих воркеров, иначе интеграция станет ручным 3-way merge.

4. **Барьер — только по необходимости.** Синхронизируй (жди всех) лишь когда следующий шаг
   реально нужен весь предыдущий результат: интеграция/merge, дедуп находок, «0 найдено → пропустить
   верификацию». Флаттен/маппинг/фильтр — не повод для барьера, делай их внутри следующего шага.
   Не держи быстрых воркеров в ожидании самого медленного без причины.

5. **Контекст-дисциплина воркеров.** Субагент НЕ наследует историю — Supervisor собирает ему
   ровно нужный контекст (входные файлы, контракт, критерии приёмки) и требует **терсовый
   возврат** (только вывод/дифф/вердикт, не пересказ). Это бережёт окно Supervisor для координации.

6. **Критичные решения — голосованием.** Для необратимого/дорогого (архитектурный выбор, легал-риск,
   ключевой PR) — несколько воркеров независимо, затем сравнение/синтез (parallelization-voting).

## 4. Definition of Done (гейты — реальные цели репо)

Задача разработки не «готова», пока локально не зелено (`verification-before-completion` — доказательства до утверждений):

```bash
make lint    # ruff check + ruff format --check + mypy + lint-imports (4 контракта гексагона)
make test    # pytest (U/C/I); для LLM-функций — ещё и пройденный eval-порог
```

- **TDD строго** (AGENT_GUIDE §1): тест первым, увидеть красным, затем минимальный код. Красные коммиты запрещены.
- **Слои** (import-linter, 4 контракта): `domain←ports←application←(adapters|bot|worker)`; domain чист (stdlib+pydantic); `app.mcp` тонкий.
- **LLM** — только через `LlmPort`/instructor/OpenRouter; модель из конфига (хардкод = провал); промпт = версионируемый файл; изменил промпт → прогон eval + сравнение отчётов.
- **Скрейпинг** — анти-бот классифицируется и **эскалируется, не обходится** (constitution IV / S5 / ст.272 УК РФ). Обход = стоп.
- **Деплой только тегом** (`git tag vX.Y.Z` → CI→GHCR→`deploy.yml` checkout+pull). НИКОГДА `git pull + up -d` на VPS. Прод-DB мутации выполняет владелец сам (CC-классификатор блокирует).

## 5. Формат делегирования (в каждом задании воркеру)

- **Контекст:** фаза, входные артефакты (пути к файлам/контрактам), что за фича.
- **Задача:** один проверяемый результат.
- **Выход:** путь к файлу/коду + формат; требование терсового возврата.
- **Ограничения:** AGENT_GUIDE + constitution, SDD-контур §2, гейты §4, TDD, что НЕ делать (напр. «не обходить анти-бот», «не трогать чужой слой»).
- **Приёмка:** критерии, по которым Supervisor примет артефакт (тест-кейсы, DoD, eval-порог).

## 6. Процессные скиллы — до действий

Правило глобального CLAUDE.md действует: при ≥1% применимости процессного скилла — открыть его ДО
работы. Ключевые связки для JobPilot: любой баг/красный тест → `systematic-debugging`;
реализация → `test-driven-development`; «готово» → `verification-before-completion`;
2+ независимых задач → `dispatching-parallel-agents` + `using-git-worktrees`;
завершение ветки → `requesting-code-review` → `finishing-a-development-branch`.
