# Research: CRM, хранилище, письма, MCP (Этап 6)

## 1. Миграция `seen_vacancy`/`labeled_vacancy` → `vacancy` (под-этап 6A)

**Контекст.** Сейчас `seen_vacancy` — рабочий реестр виденных: `source_ref` (uq, S1), `content_hash`, `normalized_key` (S2), снапшот (title/company/url/description_text/salary_*), скор (score/reason/prompt_version/model/scored_at, R1), `first_seen_at`, `digest_sent_at`. `labeled_vacancy` — снапшоты размеченных 👍/👎 с колонкой `embedding vector(768)` (пока пустой). Этап 6 требует полное `vacancy` (§3.1 + `raw jsonb`, `duplicate_of`, `canary`), поверх которого встают Application/письма/MCP.

**Варианты.**
- **A. Новая таблица + dual-write + backfill + cutover** (классический zero-downtime expand/contract). Плюс: работает под нагрузкой без окна. Минус: временный двойной путь записи, лишний код, для single-owner overkill.
- **B. Rename + additive-колонки + backfill в одной миграции** (выбрано). `seen_vacancy` уже является суперсетом «рабочих полей» `vacancy`; переименовываем таблицу в `vacancy`, добавляем `raw jsonb NOT NULL DEFAULT '{}'`, `duplicate_of text NULL`, `canary bool NOT NULL DEFAULT false`; `id` сохраняется (важно — на него сошлётся `application.vacancy_id`). `labeled_vacancy` остаётся как есть (его `embedding` наполняется в 6D). Индексы (`uq source_ref`, `normalized_key`) переезжают с таблицей.

**Решение — B.** Обоснование: система single-owner, ежедневный дайджест (10:00 МСК) → короткое окно миграции ничего не стоит; данные не теряются (rename сохраняет строки и id); инварианты S1/S2/R1 держатся теми же колонками и индексами. Backfill `raw` для исторических строк: `{"description": description_text}` (оригинального HTML для старых строк нет — допустимо, `raw` для них = очищенный текст; новые вакансии пишут полный `raw` как сейчас в `Vacancy.create`). `duplicate_of` исторически NULL (в реестре дубликаты не хранились отдельно — они не попадали в seen с пометкой; для новых работает S2 как прежде). `canary=false` для всех исторических.

**Влияние на код (6A).** ORM-класс `SeenVacancy` → `Vacancy` (models.py) с новыми колонками; `SeenVacancyRepository` ретаргетится на `vacancy` (сигнатуры портов не меняются — CRM/аналитика получают репозиторий поверх `vacancy`). Никакие use cases скоринга/дайджеста семантику не меняют. Тест миграции ([F-I1]) — на копии/фикстуре: count сохранён, uq работает, повторный upgrade идемпотентен.

**Риск.** Если позже понадобится zero-downtime под нагрузкой — вариант A остаётся открытым (ADR). Для этапа 6 фиксируем B.

## 2. Агрегат `Application` и статусная машина (под-этап 6B)

**Решение.** Статусная машина §3.3 — чистый домен `app/domain/crm/`: `ApplicationStatus` (StrEnum), `RejectStage`, `InterviewRoundKind`, агрегат `Application` с методами `apply()`, `to_interview()`, `add_round(kind)`, `to_offer()`, `reject(stage)`, `add_interview_details(url?, notes?)`. Недопустимый переход → `IllegalTransition` (переиспользуем имя ошибки из networking §3.3 — единообразие). Раунды — value objects с `ordinal`; правило «строго по возрастанию» проверяется в агрегате, добавление только в статусе `interview` (C2, [C-U2]).

**Property-тесты (constitution II, [C-U1]).** `hypothesis`: перебор всех пар `(from,to)` статусов и произвольных последовательностей раундов; инвариант — допустимы только переходы §3.3, любое нарушение оставляет состояние неизменным и бросает `IllegalTransition`. Отдельные property-тесты на `reject_stage` по источнику (из `applied` → `{pre_hr,hr}`; из `interview` → `{hr,tech,final}`, [C-U3]) и на монотонность раундов.

**C1 (один активный Application).** Уникальность на уровне БД: частичный уникальный индекс `uq_application_active_vacancy (vacancy_id) WHERE deleted_at IS NULL` (или таблица без soft-delete — удаление = DELETE строки, тогда просто `unique(vacancy_id)`; удаление разрешено из любого статуса — это не переход). Выбор: **hard delete** (`DELETE`) + `unique(vacancy_id)` — проще, удаление освобождает вакансию для нового 💾 ([C-U4], edge case).

## 3. pgvector: тип индекса, размерность, наполнение (под-этап 6D)

**Размерность.** 768 — уже зафиксирована в `labeled_vacancy.embedding vector(768)` (модель этапа 0). Модель эмбеддингов — из конфига `LLM_MODEL_EMBEDDING` (напр. `google/text-embedding-004` или совместимая через OpenRouter/прямой адаптер), выдающая 768-мерный вектор; смена модели с иной размерностью — отдельный ADR + миграция типа колонки.

**Тип индекса.** Для single-owner с сотнями–тысячами размеченных — объём мал. **HNSW** (`vector_cosine_ops`) — лучше recall/латентность на малых-средних объёмах, не требует обучения списков (в отличие от IVFFlat, которому нужен репрезентативный набор до `CREATE INDEX`). Решение: **HNSW cosine** (`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`), миграция 0007. Расстояние — косинусное (эмбеддинги нормализованы провайдером). Фолбэк: при `< FEWSHOT_MIN_EMBEDDED` размеченных с эмбеддингами — «последние N» ([R-U2]-совместимо).

**Наполнение.** Backfill эмбеддингов для исторических `labeled_vacancy` — идемпотентный скрипт/джоб (не миграция: LLM-вызовы в миграции запрещены), считает embedding по `description_text`, пишет через `EmbeddingPort`, каждый вызов → `llm_call` (purpose=`embedding`, O1). Новые метки считают embedding при разметке.

**Сравнительный eval [R-E2].** Расширяем `eval/runners/relevance.py`: два прохода few-shot-селектора (семантический vs «последние N») на одном датасете `relevance`, метрика — agreement rate/F1; порог — семантический ≥ базового; отчёт с обеими строками (как уже сделано для MODEL_B). Селектор переключается флагом раннера/конфигом, без ветвления в домене скоринга (селектор — стратегия за портом).

## 4. FastMCP: транспорт, туннель, авторизация (под-этап 6F)

**Транспорт.** FastMCP поверх **stdio** для подключения Claude Desktop через SSH (`ssh -t vps mcp-run`) — наружу порт не публикуется, UFW только 22 (PLAN.md §4, MCP3). Альтернатива HTTP/SSE отвергнута: требует публикации порта/reverse-proxy — лишняя поверхность атаки для одного пользователя.

**Авторизация.** Обязательный `MCP_AUTH_TOKEN` (env, секрет): сервер отклоняет вызовы без/с неверным токеном до вызова инструмента ([P-C1]). Плюс сетевая изоляция (localhost/туннель) — двойная защита (MCP3).

**Слои (MCP1, [P-C2]).** `app/mcp/` — тонкий интерфейсный слой поверх `application/` use cases; import-linter контракт: `app/mcp` НЕ импортирует `app.adapters.persistence`/SQLAlchemy. Инструменты дергают те же use cases, что и бот (`ListVacancies`, `GetVacancy`, `SearchSaved`, `GetCosts`, `FunnelStats`, `SetStatus`, `RunDigest`).

**Белый список write (MCP2, [P-U1]).** Реестр инструментов с флагом `write: bool`; фабрика регистрации падает, если write-инструмент не входит в `{set_status, run_digest}`. Тест перебирает все зарегистрированные.

**Read-роль Postgres (MCP4, [P-I1]).** Отдельная роль `mcp_ro` с `GRANT SELECT` (и точечными grants для write-инструментов через отдельные use cases, идущие под своей ролью, либо write-инструменты используют основную роль приложения, а read-инструменты — `mcp_ro`; для этапа: read-инструменты → `MCP_DB_DSN` под `mcp_ro`, write — через основной пул). Роль создаётся ops-скриптом деплоя (не alembic, т.к. это GRANT/CREATE ROLE — инфраструктурный шаг; фиксируется в quickstart/env). Тест [P-I1]: запись под read-ролью мимо белого списка → ошибка прав БД.

## 5. Анти-галлюцинации в сопроводительных письмах (под-этап 6E)

**Промпт.** `letter_v1.md`: system — «пиши только на основании приведённого резюме; не выдумывай факты, компании, метрики, которых нет в резюме; русский язык; ≤2000 знаков». Резюме EM и рекомендации консультанта (`resumes/`) подаются как контекст-данные; текст вакансии — как недоверенные данные (экранируется, R5-аналог). Модель — `LLM_MODEL_LETTERS` (уже `google/gemini-2.5-pro`).

**Схема.** `CoverLetterOut(text: str<=2000)`; невалидно → 1 retry → graceful (кнопка 🔁 для владельца).

**Eval `cover_letter` [M-E2] (блокер hallucinations=0).** LLM-as-judge: для каждого фактологического утверждения письма судья проверяет наличие подтверждения в резюме (fact-check), возвращает список неподтверждённых фактов; `hallucinations = число неподтверждённых`. Порог — строго 0 (блокер PR). Рубрика (дополнительно): обращение к конкретной вакансии, 1–2 релевантные метрики из резюме, ≤2000 знаков, без канцелярита. Судья — `LLM_MODEL_JUDGE`; инфра-сбои судьи — вне знаменателя (паттерн invite_rubric). До реального LLM — стаб-письмо + CI-eval в fake-режиме.

**Приватность (M4, constitution IV).** Тела писем не логируются; в `cover_letter` хранится текст (нужен для 🔁/✏️ и истории) — это данные владельца в его же БД, не лог.

## 6. HR-извлечение (под-этап 6G)

**Задача.** Из пересланного HR-сообщения извлечь `{date?, url?, gist}`; заполнить `interview_url`/`notes` заявки, **не меняя статус** (C3). LLM-задача `hr_extract` через `LlmPort`, схема `HrDetails(date: date|None, url: str|None, gist: str<=200)`, промпт `hr_extract_v1.md`, текст сообщения — недоверенные данные (экранируется, не может инициировать действия — R5/C3).

**Eval `hr_extract` [C-E1] (≥0.9).** Датасет ≥15 обезличенных сообщений HR → эталон `{date, url, gist}`; accuracy по дате и ссылке ≥0.9. Раннер — новый `eval/runners/hr_extract.py` + диспетчер в `run.py`; порог в `THRESHOLDS`.

**Разделение 6B/6G.** 6B поставляет «➕ собес» с ручным заполнением (владелец сам вводит/вставляет ссылку) — работает без LLM. 6G добавляет автоизвлечение поверх той же плумбинг-точки (use case `AddInterviewDetails` получает второй путь заполнения). Инкрементально по TDD.

## 7. Порядок миграций и предотвращение конфликтов

Общие файлы этапа: `models.py`, `composition.py`, `config.py`, `alembic/versions/`. Чтобы под-этапы велись отдельными агентами с минимумом конфликтов — номера миграций и down_revision фиксируются заранее (линейная цепочка по порядку мержа).

**⚠️ Актуальный head миграций.** На момент планирования в проекте: `0004_stage3` — последняя закоммиченная; этап 4 (getmatch) миграцию не добавлял; этап 5 (sites) **в работе** и занимает `0006_stage5` (down_revision `0004_stage3`). Этап 6 чейнится **поверх stage-5 head** (`0006_stage5`), т.к. этап 5 мержится раньше. Если при мерже stage-5 будет перенумерован (напр. в `0005`), оркестратор ребейзит down_revision первой миграции этапа 6 на фактический head — цепочка остаётся линейной.

| Миграция | Под-этап | down_revision | Содержимое |
|---|---|---|---|
| `0007_stage6a_vacancy` | 6A | `0006_stage5` (stage-5 head) | rename seen_vacancy→vacancy + колонки raw/duplicate_of/canary + backfill |
| `0008_stage6b_application` | 6B | `0007_stage6a_vacancy` | application + interview_round + uq(vacancy_id) |
| `0009_stage6d_pgvector` | 6D | `0008_stage6b_application` | HNSW-индекс на labeled_vacancy.embedding |
| `0010_stage6e_cover_letter` | 6E | `0009_stage6d_pgvector` | cover_letter |

6C/6F/6G схему не меняют (6F — GRANT/CREATE ROLE ops-скриптом). Если 6D/6E мержатся раньше 6B — down_revision правится на фактического предшественника (разрешается оркестратором при мерже; цепочка остаётся линейной). Правки `models.py`/`composition.py`/`config.py` каждый под-этап делает в своей секции (аддитивно), конфликты — только в местах регистрации, разрешаются тривиально.
