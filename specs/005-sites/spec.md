## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вакансии карьерных порталов в дайджесте (Priority: P1)

Владелец подписан на дайджест EM-вакансий. К уже работающим источникам (HH-email, GetMatch) добавляются карьерные порталы крупных технокомпаний (10 сайтов). Каждый портал — отдельный адаптер `VacancySourcePort`, который тянет список вакансий, фильтрует руководящие/EM-роли на своей стороне (чтобы не гнать в скоринг сотни нерелевантных карточек), маппит карточку в доменный `Vacancy` с `Source.SITE` и `site_name`, и отдаёт в общий конвейер Sourcing → Relevance → Delivery. В карточке дайджеста видно, что источник — конкретный сайт (пометка `site:<name>`).

**Why this priority**: это продукт этапа — расширение покрытия вакансий прямыми источниками работодателей, минуя агрегаторы. Всё остальное (канарейка, golden, метрики) — обвязка вокруг доставки вакансий сайтов в дайджест.

**Independent Test**: включить один сайт (например, `yandex`) → в дневном дайджесте появляется секция/пометка вакансий этого сайта со скором; ссылка карточки открывает реальную вакансию на портале.

**Acceptance Scenarios**:

1. **Given** golden-ответ карьерного портала, **When** адаптер парсит, **Then** список `VacancyDTO` с field completeness: title/url 100%, company 100% (= имя компании адаптера), location ≥90% ([S-C7]).
2. **Given** адаптер сайта фильтрует по EM/лид-ключам из конфига, **When** портал вернул 300 вакансий, из которых 8 руководящих, **Then** в конвейер уходят только прошедшие фильтр (остальное отсекается до скоринга — экономия токенов; фильтр адаптерный, не доменный).
3. **Given** вакансия сайта прошла скоринг ≥ threshold, **When** формируется дайджест, **Then** карточка содержит пометку источника `site:<name>` и рабочую ссылку (S3: `description_text` очищен, `raw` сохранён).
4. **Given** вилка «от X» без «до», **Then** `Salary(from=X, to=None)`; вилки нет → `Salary(None,None,None)` (все поля опциональны, §3.1).

### User Story 2 - Изоляция падений и golden-diff как регресс-сигнал (Priority: P1)

Карьерные порталы — недоверенная внешняя среда, которая молча меняет вёрстку/структуру ответа. Падение или «поплывший» парсер одного сайта не должно ронять сбор из остальных сайтов и из HH/GetMatch. Каждый сайт защищён golden-тестом: изменилась структура ответа — тест падает с понятным diff-сигналом «скрейпер `<site>` сломан», а рантайм в этот момент инкрементит `scraper_failures{site}` и продолжает работу.

**Why this priority**: без изоляции падений и регресс-сигнала хрупкие источники превращаются в точки отказа дневного пайплайна (нарушение S4).

**Independent Test**: подменить golden одного сайта (сломать структуру) → `pytest` этого сайта красный с diff; в рантайме тот же сайт бросает исключение → job завершается `partial`, вакансии остальных сайтов и HH/GetMatch собраны.

**Acceptance Scenarios**:

1. **Given** структура ответа сайта изменилась (модифицированный golden), **When** тест, **Then** падение с diff — сигнал «скрейпер сломан» ([S-C8]).
2. **Given** портал вернул 0 вакансий или 5xx, **When** сбор, **Then** `SourceFetchFailed(source="site:<name>")` + инкремент `scraper_failures{site}`, остальные сайты собраны ([S-C9], S4).
3. **Given** любой адаптер сайтов, **When** несколько запросов, **Then** между запросами ≥1 сек (rate limit) и `User-Agent` из конфига ([S-C10]).
4. **Given** портал показывает капчу/анти-бот-стену/требует логина, **When** fetch, **Then** `SourceFetchFailed(source="site:<name>", error="anti_bot")` + эскалация владельцу; капча НЕ обходится (S5, constitution IV); остальные источники собраны.

### User Story 3 - Канарейка нового сайта до одобрения (Priority: P1)

Новый скрейпер не заслуживает доверия сразу: его вакансии 2–3 дня идут в дайджест **отдельной секцией «На проверку (canary)»** — видны владельцу, но помечены как непроверенные. Владелец наблюдает качество (полнота полей, релевантность, отсутствие мусора) и, убедившись, даёт команду `/approve_scraper <site>` — с этого момента сайт вливается в основной поток дайджеста наравне с HH/GetMatch.

**Why this priority**: человек в контуре (constitution VI) — новый источник проходит canary до явного одобрения; без этого нельзя безопасно включать неизвестные по качеству источники.

**Independent Test**: включить сайт в canary → его вакансии приходят в секции «На проверку», а не в основной; `/approve_scraper yandex` → следующий дайджест несёт вакансии `yandex` в основном потоке.

**Acceptance Scenarios**:

1. **Given** сайт в списке активных, но не одобрен, **When** дайджест, **Then** его вакансии — в секции «На проверку (canary)» с пометкой `site:<name> · canary`.
2. **Given** `/approve_scraper <site>` от владельца, **When** следующий дайджест, **Then** вакансии сайта в основном потоке; факт одобрения персистится (переживает рестарт).
3. **Given** `/approve_scraper <неизвестный_site>`, **Then** вежливый отказ со списком доступных сайтов; состояние не меняется.
4. **Given** DRY_RUN=true, **When** прогон, **Then** дайджест помечен «ТЕСТ», внешних записей нет (сбор с сайтов — чтение, записи на порталы у этапа нет по построению).

### Edge Cases

- **Сайт — SPA без SSR и без обнаруженного JSON-эндпоинта** → адаптер требует Playwright/Chromium; на текущем железе (1 vCPU / ~1 GB, swap 0 — INFRA.md) браузер не помещается (+300–700 MiB) → задача сайта помечена «тяжёлой» и **гейтится апгрейдом железа**; до апгрейда сайт в конфиге выключен, метрика `scraper_failures` не капает (источник не активирован).
- **robots.txt запрещает раздел вакансий** → сайт не скрейпится, фиксируется открытым вопросом владельцу (уважение robots.txt — жёсткое ограничение); альтернатива — официальный JSON-эндпоинт, если он вне запрета.
- **Портал внезапно включил анти-бот (Qrator/Cloudflare/капча)** для ранее «лёгкого» сайта → `SourceFetchFailed(error="anti_bot")`, эскалация, S5; обход не строим.
- **Дубли между сайтом и HH/GetMatch** (одна вакансия и на портале, и в подписке HH) → кросс-источниковый дедуп по нормализованной (company, title) за 30 дней (S2) — существующий доменный механизм, сайт-адаптер ничего не добавляет.
- **Портал вернул вилку строкой «з/п не указана» / текстовый диапазон** → `Salary` с опциональными полями; неразобранное не попадает в `company`/`title` (S3, аналогично [S-C0]).
- **Кириллица/не-ASCII в параметрах запроса и ссылках** → корректное URL-кодирование; ссылка на карточку абсолютная и открывается.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять по одному адаптеру `VacancySourcePort` на каждый из 10 порталов (Яндекс, VK, Avito, Т-Банк, Ozon, Альфа, Сбер, Navio, МТС, RWB/Wildberries); каждый адаптер маппит карточку портала в доменный `Vacancy` c `SourceRef(source=SITE, site_name=<name>, external_id)` и опциональным `Salary` ([S-C7]). Домен Sourcing НЕ меняется (DOMAIN.md §5).
- **FR-002**: Каждый адаптер MUST предпочитать доступ **без браузера**: публичный JSON/GraphQL-эндпоинт списка вакансий (XHR фронта) или server-rendered HTML через `httpx`; Playwright применяется ТОЛЬКО когда сайт — SPA без SSR и без обнаруженного JSON-эндпоинта (research.md фиксирует выбор per-site).
- **FR-003**: Парсинг MUST быть чистой функцией `parse_<site>(payload) -> list[VacancyDTO]` (без I/O), покрытой golden-тестом на записанном ответе; изменение структуры ответа → падение golden с diff-сигналом ([S-C8]).
- **FR-004**: Каждый адаптер MUST фильтровать вакансии по EM/лид-ключам из конфига на своей стороне ДО передачи в конвейер (руководящие/инженерно-менеджерские роли), чтобы не гнать нерелевантное в скоринг; фильтр адаптерный, домен и скоринг не трогаются.
- **FR-005**: Сбор MUST быть отказоустойчив: падение/пустой ответ/5xx/анти-бот одного сайта → `SourceFetchFailed(source="site:<name>")` + инкремент `scraper_failures{site}`, остальные источники собираются (S4, [S-C9]); job → `partial`.
- **FR-006**: Каждый адаптер MUST соблюдать вежливость: ≤1 запрос/сек (rate limit из конфига), честный `User-Agent` из конфига, уважение `robots.txt` целевого раздела ([S-C10]). Капча/анти-бот НЕ обходятся — `SourceFetchFailed(error="anti_bot")` + эскалация (S5, constitution IV).
- **FR-007**: MUST существовать механизм канарейки: сайт из `SITES_CANARY` отдаёт вакансии в отдельную секцию дайджеста «На проверку (canary)» до команды `/approve_scraper <site>`; факт одобрения персистится; неизвестный сайт → отказ (constitution VI, DOMAIN.md §1 «Канарейка»).
- **FR-008**: MUST существовать eval-контекст `sites_parse` per-site: field-completeness отчёт по каждому сайту; регресс completeness >5% против прошлого отчёта = блокер ([S-E2]).
- **FR-009**: Список активных сайтов, canary-список, паузы/лимиты, EM-ключи, User-Agent — только из env/конфига (contracts/env.md); секретов у этапа нет (порталы публичны). «Тяжёлые» (Playwright) сайты по умолчанию выключены до апгрейда железа.
- **FR-010**: Наблюдаемость (constitution V): каждый сбор с сайта — child span; метрика `scraper_failures{site}`; счётчик собранных/отфильтрованных вакансий per-site в `job_run`.

### Key Entities

- **Vacancy / SourceRef / Salary** (DOMAIN.md §3.1) — переиспользуются без изменений; новизна этапа — значение `Source.SITE` + `site_name` ∈ {yandex, vk, avito, tbank, ozon, alfa, sber, navio, mts, rwb}.
- **VacancyDTO** — контракт `VacancySourcePort.fetch()`; тот же, что у HH/GetMatch.
- **Одобрение сайта (approval)** — факт `/approve_scraper <site>`: персистится (минимальный слой хранения, см. data-model.md), не доменный агрегат.
- **Конфиг сайтов** — активные/canary/тяжёлые списки, лимиты, UA, EM-ключи — env.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Golden-тесты всех включённых сайтов зелёные; модифицированный golden падает с diff ([S-C7], [S-C8]).
- **SC-002**: Вакансии сайтов появляются в дайджесте с пометкой источника `site:<name>`; canary-вакансии — в секции «На проверку» до `/approve_scraper` ([S-C9], acceptance PLAN.md §6).
- **SC-003**: Падение одного сайта → job `partial`, `scraper_failures{site}` инкрементнут, остальные источники собраны (S4, [S-C9]); grep/архитектурный тест: между запросами ≥1 сек, UA из конфига ([S-C10]).
- **SC-004**: `make eval CONTEXT=sites_parse` даёт per-site completeness-отчёт; регресс >5% = блокер ([S-E2]).
- **SC-005**: Ни одного обхода капчи/анти-бота в коде: анти-бот → `SourceFetchFailed(error="anti_bot")` + эскалация (S5, constitution IV).
- **SC-006**: 🖐 Ручная проверка: владелец наблюдает 3-дневную канарейку по каждому включённому сайту и даёт `/approve_scraper <site>`.

## Assumptions

- **Разделение «лёгкие/тяжёлые» (research.md)**: лёгкие (SSR HTML / JSON через httpx, без браузера) запускаются на текущем железе; тяжёлые (Playwright/Chromium) — гейтятся апгрейдом до 4 vCPU / 8 GB (INFRA.md §4.2). По итогам разведки на 2026-08-12: подтверждённо лёгкие — **Яндекс, VK, Avito** (SSR, вакансии в HTML); кандидаты в лёгкие через обнаруживаемый JSON-эндпоинт (нужна проверка XHR в devtools) — **Сбер, Т-Банк, Альфа**; тяжёлый/анти-бот — **Ozon** (редирект-петля при серверном запросе). Точная классификация Сбер/Т-Банк/Альфа/Ozon — открытый вопрос, закрывается спайком в tasks.md.
- **Каталог сайтов (10) и их статус** (сверено с docs/legal/scraping-risks.md §3–3a на 2026-08-14):
  - **Яндекс** 🟢* — SSR-HTML, лёгкий (Волна A, активен).
  - **VK** 🟢* — SSR-HTML, лёгкий (Волна A, активен).
  - **Avito career** 🟢* — SSR-HTML career-сабдомен, лёгкий (Волна A, активен).
  - **Сбер** 🟡 — публичный JSON `/search`, лёгкий (Волна B, активен).
  - **Т-Банк** 🟡 — публичный `POST /pfpjobs/papi/getVacancies`, лёгкий (Волна B, активен; XHR-спайк 2026-08-13 подтвердил тело запроса).
  - **Альфа** 🟡 — спайк JSON-эндпоинта не закрыт → **отложен** (Волна B, T522 open).
  - **Ozon** 🔴 — Qrator редирект-петля на job/career-сабдоменах → **заблокирован**, не активируется без обхода (Волна C, гейт железа; S5).
  - **Navio** (navio.auto/vacancies) 🟢* — публичный встроенный JSON-фид (Gatsby `window.pageData`), лёгкий (Волна D, активен).
  - **МТС** (job.mts.ru) 🟡 — публичный каталог `GET /api/v2/catalog/v1/vacancies`, домен за анти-DDoS (ddos-guard); при челлендже → S5 (Волна D, активен с canary).
  - **RWB/Wildberries** (career.rwb.ru) 🟢* — публичный cookieless `GET /crm-api/api/v1/pub/vacancies`, лёгкий (Волна D, активен).
  - **MWS** (mws.ru/vacancies) 🔴 — **рассмотрен и исключён**: Qrator рвёт соединение прод-egress (VPS RU-IP → 000), в теле `yandexSmartCaptcha`; активировать нельзя, обход не строим. Адаптера НЕТ (не входит в 10).
  - Терминология волн: **A** = Яндекс/VK/Avito (SSR-HTML); **B** = Сбер/Т-Банк/Альфа (JSON после спайка); **C** = Ozon/browser_transport (гейт железа); **D** = Navio/МТС/RWB (публичные JSON-фиды карьерных порталов, построена вперёд спеки — синхронизирована ретроспективно, см. docs/decisions/ADR-001).
- Резюме — Engineering Manager; EM/лид-ключи (`SITES_EM_KEYWORDS`, дефолт — engineering manager; руководитель разработки; head of engineering; team lead; тимлид; …) фильтруют адаптерно; список правит владелец.
- Порталы публичны, кредов/секретов нет; единственное взаимодействие — чтение публичного списка вакансий с уважением robots.txt и rate-limit.
- Пометка источника в карточке — UI-строка `site:<name>`; секция «На проверку (canary)» — уже предусмотрена доменной моделью дайджеста (DOMAIN.md §1 «Дайджест», «Канарейка»).
- Пока реальный доступ к «тяжёлым» сайтам недоступен (нет апгрейда железа), их адаптеры реализуются и тестируются на golden/моках, но в рантайме выключены — паттерн «хвостов» этапов 1–4.
