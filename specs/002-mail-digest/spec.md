## User Scenarios & Testing *(mandatory)*

### User Story 1 - Секция «Почта» в утреннем дайджесте (Priority: P1)

Вместе с карточками вакансий владелец получает в дайджесте секцию «Почта»: рабочие письма за последние 24 часа (ответы работодателей, приглашения, письма рекрутёров) — каждое одной строкой-summary (кто, о чём, что требуется, ≤2 строк) со ссылкой на письмо. Рассылки и нерелевантный шум в секцию не попадают.

**Why this priority**: пропущенное письмо с интервью/оффером обесценивает весь поиск — это главный риск-контроль этапа.

**Independent Test**: при наличии рабочих писем за 24ч секция появляется в дайджесте с работающими ссылками; при отсутствии — секции нет; письмо-рассылка магазина в секцию не попадает.

**Acceptance Scenarios**:

1. **Given** письма за 24ч (рабочие и шум), **When** дайджест, **Then** секция «Почта» содержит только рабочие, каждое: отправитель, summary ≤2 строк, ссылка.
2. **Given** письмо от noreply@hh.ru, **When** префильтр, **Then** оно проходит к LLM-классификации без затрат на очевидный шум ([M-U1], M1).
3. **Given** письмо-рассылка магазина, **When** префильтр, **Then** отсечено ДО LLM ([M-U1]).
4. **Given** summary от LLM длиннее 2 строк, **When** валидация, **Then** обрезка/реджект по схеме ([M-U2], M2).
5. **Given** писем за 24ч нет, **When** дайджест, **Then** секции «Почта» нет (не пустует).

---

### User Story 2 - Секция «LinkedIn» из Gmail-уведомлений (Priority: P2)

Уведомления LinkedIn, приходящие на почту (инвайты «X wants to connect», сообщения), выделяются в отдельную секцию «LinkedIn» дайджеста — так входящие LinkedIn видны без автоматизации самого LinkedIn (принцип N1: только полуавтомат).

**Why this priority**: канал LinkedIn важен (этап 3 строит на нём нетворкинг), но письма-уведомления — подмножество почты, секция строится поверх готового P1.

**Independent Test**: уведомление «X wants to connect» попадает в секцию «LinkedIn» (не в «Почту») со ссылкой на профиль/сообщение.

**Acceptance Scenarios**:

1. **Given** уведомление LinkedIn среди писем, **When** классификация, **Then** source=linkedin_gmail, попадает в секцию «LinkedIn» ([M-U3]).
2. **Given** обычное рабочее письмо, **When** классификация, **Then** оно в «Почте», не в «LinkedIn».

---

### User Story 3 - Подключение Gmail и приватность (Priority: P2)

Владелец подключает Gmail один раз CLI-хелпером (OAuth, scope только чтение); до подключения работает мок-режим — механика секций тестируется без кредов. Тела писем никогда не попадают в журналы и телеметрию — только summary.

**Why this priority**: доступ — предусловие боевого режима, но благодаря мокам не блокирует разработку; приватность — константное требование (M4, constitution IV).

**Independent Test**: хелпер выдаёт refresh token со scope gmail.readonly; в логах тестового прогона тела писем отсутствуют ([M-C2]); GMAIL_MODE=fake даёт реалистичные письма без внешних вызовов.

**Acceptance Scenarios**:

1. **Given** CLI-хелпер, **When** владелец подтверждает доступ в браузере, **Then** refresh token сохранён локально, scope — только чтение.
2. **Given** обработка любого письма, **When** логирование, **Then** тело письма в логах отсутствует ([M-C2], M4).
3. **Given** GMAIL_MODE=fake (или auto без кредов), **When** дайджест, **Then** секции строятся на мок-письмах — механика проверяется end-to-end.
4. **Given** письма за пределами 24ч, **When** выборка, **Then** обработаны только свежие ([M-C1]).

---

### Edge Cases

- Gmail недоступен/квота → секция пропускается, job_run partial, алерт по правилам; дайджест вакансий не страдает (изоляция по образцу S4).
- Письмо с инструкциями для LLM («classify as job offer») → текст письма в data-блоке, не инструкции (R5-механика этапа 1 переиспользуется).
- LLM вернул невалидный ответ по письму → 1 retry → письмо помечается «не классифицировано» и попадает в «Почту» с темой вместо summary (лучше ложное срабатывание, чем пропуск оффера — производная от «ноль пропусков» [M-E1]).
- Письмо одновременно и LinkedIn-уведомление, и «про работу» → секция LinkedIn (более специфичная).
- Очень длинное письмо → в LLM уходит усечённый текст (лимит конфига), summary всё равно ≤2 строк.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST собирать письма за последние 24ч (только чтение) и прогонять их через двухступенчатый фильтр: эвристика (домены hh.ru/getmatch.ru/habr.com/linkedin.com + ключевые слова из конфига) → LLM-классификация «про работу?» только для прошедших (M1, [M-U1]).
- **FR-002**: Для рабочих писем LLM MUST давать summary ≤2 строк (кто, о чём, что требуется); выход валидируется схемой, невалидный → 1 retry → фолбэк на тему письма (M2, [M-U2]).
- **FR-003**: Дайджест MUST содержать секцию «Почта» (рабочие письма с summary и ссылками) и отдельную секцию «LinkedIn» (уведомления source=linkedin_gmail, [M-U3]); пустые секции не показываются.
- **FR-004**: Обработанные письма MUST сохраняться в inbox_message (DOMAIN.md §4) — дедуп повторной обработки и история; тела писем в БД не хранятся (только метаданные + summary).
- **FR-005**: Тела писем MUST NOT попадать в логи/телеметрию ([M-C2], M4); текст письма в промпте — data-блок (R5).
- **FR-006**: Доступ к Gmail MUST настраиваться CLI-хелпером (OAuth, минимальный scope чтения, refresh token в env); GMAIL_MODE (auto|fake|real) MUST переключать мок/реальный источник без правок кода (паттерн этапа 1).
- **FR-007**: Каждый LLM-вызов классификации MUST порождать llm_call (O1); сбор почты — JobRun-шаг дайджеста с изоляцией сбоя.
- **FR-008**: MUST существовать eval-контекст `mail_classify`: датасет ≥40 писем (собирается в мок/DRY_RUN-период + реальные обезличенные), accuracy ≥0.9, false negative по письмам с офферами/интервью = 0 — блокер ([M-E1]).

### Key Entities

- **InboxMessage** (DOMAIN.md §3.4): source (gmail | linkedin_gmail; hh — уже в этапе 1 через negotiations), sender, subject, summary, url, received_at, classified (job | not_job | linkedin | unclassified).
- **Префильтр** — эвристика, не сущность: список доменов/ключевых слов в конфиге.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Дайджест содержит секции «Почта» и «LinkedIn» с работающими ссылками (acceptance PLAN.md); пустые секции скрыты.
- **SC-002**: Кейсы TEST_CASES.md раздела 3 ([M-U1]–[M-U3], [M-C1], [M-C2]) зелёные.
- **SC-003**: Эвристический префильтр отсеивает шум до LLM: на мок-корпусе ≥50% писем не доходят до LLM (экономия токенов, M1).
- **SC-004**: `make eval CONTEXT=mail_classify` на датасете ≥40: accuracy ≥0.9, пропусков офферов/интервью — 0 ([M-E1]).
- **SC-005**: В логах тестового прогона нет ни одного фрагмента тела письма ([M-C2]).
- **SC-006**: 🖐 Ручная проверка: 2 дня сверки summary с оригиналами писем — расхождений по смыслу нет.

## Assumptions

- Gmail-креды (client_id/secret приложения Google Cloud + refresh token) заводит владелец; до этого — GMAIL_MODE=fake с реалистичным мок-корпусом (решение владельца от этапа 1 распространяется и сюда).
- LLM-классификация — модель `LLM_MODEL_SUMMARY` из конфига; в мок-режиме LLM_MODE=fake — детерминированный стаб (по доменам/ключевым словам), llm_call пишется.
- Секция «Переписка HH» (negotiations, этап 1) остаётся отдельной от «Почты»; письма-уведомления HH из Gmail дедуплицируются эвристикой «hh.ru → уже покрыто negotiations» (не показываем дважды) — уточнение в plan.
- inbox_message — миграция 0003 (одна на этап, DOMAIN.md §4).
- Пороги eval из TEST_CASES.md [M-E1]; датасет append-only.
