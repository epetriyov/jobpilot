## User Scenarios & Testing *(mandatory)*

### User Story 1 - Владелец получает работающий, безопасный фундамент системы (Priority: P1)

Владелец (единственный пользователь) поднимает всю систему одной командой на чистой машине. Telegram-бот отвечает только ему; сообщения посторонних молча игнорируются и фиксируются в журнале. Система стартует только при полностью заданной конфигурации: при отсутствии обязательного параметра она сообщает его имя и не запускается, вместо того чтобы падать позже посреди работы.

**Why this priority**: без воспроизводимого и безопасного фундамента ни один следующий этап (HH, почта, LinkedIn…) не может быть построен и проверен; это MVP этапа.

**Independent Test**: на чистой машине выполнить запуск с заполненной конфигурацией → сервисы работают, бот отвечает владельцу и игнорирует чужой chat_id; убрать обязательную переменную → понятная ошибка, сервис не стартует.

**Acceptance Scenarios**:

1. **Given** чистая машина с заполненной конфигурацией, **When** запуск окружения одной командой, **Then** все сервисы (бот, обработчик задач, БД, коллектор телеметрии) поднимаются, схема БД создаётся, бот отвечает владельцу.
2. **Given** конфигурация без обязательной переменной, **When** старт сервиса, **Then** понятная ошибка с именем переменной, сервис не стартует (кейс [F-U1]).
3. **Given** сообщение от чужого chat_id, **When** любой хендлер бота, **Then** молчаливый игнор + предупреждение в журнале (кейс [F-U2]).
4. **Given** включён режим сухого прогона (DRY_RUN), **When** полный пайплайн, **Then** внешних записей нет, а результат помечен «ТЕСТ» (кейс [F-I2]).

### User Story 2 - Владелец видит здоровье системы и получает алерты в Telegram (Priority: P2)

Владелец открывает облачный дашборд и видит: прогоны плановых задач, количество вакансий по источникам, расход и стоимость LLM-вызовов. Если плановая задача упала, дайджест не отправлен к 10:15 МСК или источники начали сыпаться — владелец получает алерт в Telegram, не заглядывая в логи.

**Why this priority**: система работает автономно по расписанию; без наблюдаемости и алертов сбой останется незамеченным на дни. Наблюдаемость — не опция (Принцип V constitution).

**Independent Test**: сгенерировать тестовые события (успешный и упавший прогон, тестовый LLM-вызов) → они видны на дашборде (трейс, метрики, логи); отправить тестовый алерт → сообщение доходит в Telegram владельца.

**Acceptance Scenarios**:

1. **Given** работающие сервисы с подключёнными кредами облачного мониторинга, **When** выполняется любой плановый прогон, **Then** его трейс, метрики и журнальные записи видны в облачном мониторинге.
2. **Given** упавший плановый прогон, **When** завершение, **Then** запись журнала прогонов имеет статус error с заполненной ошибкой и сквозным идентификатором трейса (кейс [F-I3]) и срабатывает алерт в Telegram.
3. **Given** настроенные правила алертов, **When** отправка тестового алерта, **Then** сообщение доходит в Telegram владельца.

---

### User Story 3 - Инженер (агент) защищён рельсами качества: CI, ревью, тесты, eval (Priority: P2)

Любое изменение проходит через PR: автоматический контроль стиля, типизации, границ слоёв, unit- и contract-тестов и eval на записанных ответах LLM (без внешних ключей); агент-ревьюер оставляет комментарии о соответствии спеке и constitution. Выкладка на сервер выполняется по тегу, а не вручную.

**Why this priority**: правила constitution (test-first, слои, измеряемый LLM) без автоматического контроля не работают; но проверять их можно только когда есть что коммитить (после P1).

**Independent Test**: открыть тестовый PR с нарушением (например, красный тест или импорт адаптера из домена) → CI красный; открыть корректный PR → CI зелёный и появился комментарий агента-ревьюера.

**Acceptance Scenarios**:

1. **Given** PR с корректным изменением, **When** CI, **Then** все проверки зелёные и агент-ревью оставляет комментарий.
2. **Given** PR с нарушением границ слоёв или красным тестом, **When** CI, **Then** сборка красная, мерж заблокирован.
3. **Given** опубликованный тег версии, **When** деплой-workflow, **Then** новая версия развёрнута на сервере без ручных шагов.

### User Story 4 - Учёт каждого LLM-вызова и восстановимость данных (Priority: P3)

Каждый вызов LLM (включая фейковый провайдер в тестах) оставляет учётную запись: модель, версия промпта, токены, стоимость, латентность, идентификатор трейса. Данные системы ежедневно бэкапятся и восстановимы: владелец может развернуть дамп на чистой БД.

**Why this priority**: инварианты O1 (нет вызова без учёта) и восстановимость — фундамент долгосрочной эксплуатации, но проверяются позже базового каркаса.

**Independent Test**: выполнить вызов через порт LLM на фейковом провайдере → появилась учётная запись с токенами и стоимостью; выполнить бэкап и восстановление на чистую БД → счётчики строк совпадают.

**Acceptance Scenarios**:

1. **Given** любой LLM-вызов через порт LLM, **When** вызов завершён, **Then** создана учётная запись вызова с токенами и стоимостью (кейс [F-U3], инвариант O1).
2. **Given** наполненная БД, **When** бэкап и восстановление на чистую БД, **Then** данные совпадают, ротация хранит 14 дней (кейс [X-I2]).
3. **Given** каркас eval, **When** запуск eval-команды для контекста, **Then** прогон выполняется и создаёт отчёт (пусть пока на пустом/демо-датасете).

### Edge Cases

- Что происходит, когда облачный мониторинг недоступен? Сервисы продолжают работать; телеметрия буферизуется/теряется без падения пайплайна.
- Что происходит при повторном применении миграций на уже мигрированной БД? Идемпотентность: повторный прогон ничего не ломает (кейс [F-I1]).
- Что происходит, когда LLM возвращает невалидный ответ? Один повтор, затем корректный пропуск с предупреждением — пайплайн жив (инвариант R2, кейс [R-U1] — базовая механика закладывается на этом этапе).
- Что происходит с секретами при логировании? Значения секретов никогда не попадают в журнал (кейс [X-U1]).
- Что происходит, когда один источник вакансий падает при сборе? Остальные источники обрабатываются, прогон помечается частичным (кейс [S-U4]).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST подниматься на чистой машине одной командой и включать сервисы: бот, обработчик плановых задач, БД, коллектор телеметрии.
- **FR-002**: Система MUST отказываться стартовать при отсутствии обязательного параметра конфигурации, называя его имя ([F-U1]).
- **FR-003**: Бот MUST отвечать только владельцу (единственный настроенный chat_id); чужие сообщения — молчаливый игнор + предупреждение в журнале ([F-U2]).
- **FR-004**: Система MUST хранить: реестр виденных вакансий (для дедупликации), снапшоты размеченных вакансий (для few-shot и eval), учёт LLM-вызовов, журнал прогонов задач (DOMAIN.md §4, минимальный слой).
- **FR-005**: Схема хранения MUST создаваться миграциями; повторное применение MUST быть идемпотентным ([F-I1]).
- **FR-006**: Доменная модель shared+sourcing MUST реализовывать инварианты S1–S4 (уникальность по SourceRef, кросс-источниковый дедуп, очистка описания от HTML при сохранении оригинала, изоляция падения источника) ([S-U1]–[S-U4]).
- **FR-007**: Все обращения к LLM MUST идти через единый порт; MUST существовать сменяемые реализации: реальный провайдер и фейковый для тестов; модель MUST задаваться конфигурацией без изменения кода ([R-C3]).
- **FR-008**: Каждый LLM-вызов MUST порождать учётную запись (модель, версия промпта, токены, фактическая стоимость с фолбэком на прайс из конфига, латентность, идентификатор трейса) — включая фейковый провайдер ([F-U3], инвариант O1).
- **FR-009**: Каждый плановый прогон MUST фиксироваться в журнале прогонов со статусом, счётчиками и идентификатором трейса; ошибка прогона MUST заполнять error и связываться с журналом по трейсу ([F-I3]).
- **FR-010**: Телеметрия (журналы, метрики, трейсы) MUST доставляться в облачный мониторинг через локальный коллектор; недоступность мониторинга MUST NOT ронять сервисы.
- **FR-011**: MUST существовать базовый дашборд (прогоны задач, вакансии по источникам, LLM-токены/стоимость) и алерты в Telegram владельца: упавшая задача, дайджест не отправлен к 10:15 МСК, рост сбоев скрейперов.
- **FR-012**: Режим сухого прогона (DRY_RUN) MUST выполнять пайплайн полностью без внешних записей, помечая результат «ТЕСТ» ([F-I2]).
- **FR-013**: MUST существовать ежедневное резервное копирование БД с ротацией 14 дней и проверенное восстановление ([X-I2]).
- **FR-014**: MUST существовать каркас eval: датасеты (append-only), раннеры с порогами, отчёты; запуск одной командой с указанием контекста.
- **FR-015**: CI MUST на каждом PR проверять: стиль, типизацию, границы слоёв, unit+contract тесты и eval на записанных ответах LLM — без каких-либо внешних ключей; MUST существовать агент-ревью PR и деплой по тегу.
- **FR-016**: Значения секретов MUST NOT появляться в коде, журналах и промптах ([X-U1]); секреты поступают только из окружения.

### Key Entities

- **Виденная вакансия (seen_vacancy)**: факт первого обнаружения вакансии — ссылка на источник (SourceRef), хеш содержимого, момент первого обнаружения, момент отправки в дайджест. Основа дедупликации.
- **Размеченная вакансия (labeled_vacancy)**: снапшот текста вакансии с ручным вердиктом владельца (relevant/irrelevant) и местом под эмбеддинг. Топливо few-shot и eval.
- **Вызов LLM (llm_call)**: учётная запись обращения к LLM — назначение, модель, версия промпта, токены, стоимость, латентность, идентификатор трейса.
- **Прогон задачи (job_run)**: запись о запуске плановой задачи — имя, статус (success/partial/error), счётчики входа/выхода, ошибка, идентификатор трейса.
- **Вакансия (Vacancy, домен)**: объявление о работе; уникальна по (source, site_name, external_id); зарплатная вилка опциональна.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На чистой машине окружение поднимается одной командой; бот отвечает владельцу и игнорирует 100% чужих сообщений.
- **SC-002**: CI на тестовом PR зелёный; агент-ревью оставляет как минимум один комментарий; PR с намеренным нарушением слоёв — красный.
- **SC-003**: Телеметрия тестового прогона (трейс + метрики + журнал) видна в облачном мониторинге; тестовый алерт доходит в Telegram владельца.
- **SC-004**: 100% LLM-вызовов через порт (включая тестовые на фейковом провайдере) имеют учётную запись с токенами и стоимостью.
- **SC-005**: Все кейсы раздела 0 TEST_CASES.md ([F-U1], [F-U2], [F-U3], [F-I1], [F-I2], [F-I3]) и сквозные ([X-U1], [X-I2]) реализованы тестами и зелёные.
- **SC-006**: Команда eval-запуска отрабатывает и создаёт отчёт в каталоге отчётов.
- **SC-007**: Бэкап-восстановление: после восстановления дампа на чистую БД счётчики строк совпадают с исходной БД.

## Assumptions

- Единственный пользователь — владелец; идентифицируется одним chat_id из конфигурации (PLAN.md §2).
- Облачный мониторинг — бесплатный тариф Grafana Cloud; аккаунт заводит владелец и передаёт креды (ручной шаг этапа); до передачи кредов телеметрия проверяется локально через коллектор.
- Полноценный дайджест-пайплайн появится на этапе 1; на этапе 0 «полный пайплайн» для [F-I2]/[X-I1] — это смоук-прогон на фикстурах, проходящий все шаги (сбор → дедуп → скоринг фейковым провайдером → отправка) в DRY_RUN.
- Секреты для интеграций (Telegram-токен, ключ LLM-провайдера, креды мониторинга, SSH-доступ) предоставляет владелец; система нигде их не изобретает и не хранит вне окружения.
- Деплой-цель — VPS владельца, доступный по SSH; до предоставления доступа деплой-workflow проверяется до шага подключения (создание секретов — ручной шаг).
- Кросс-источниковый дедуп (S2) реализуется в домене на этом этапе; полноценная проверка на нескольких реальных источниках — этап 1+.
