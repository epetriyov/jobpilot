# Feature Specification: Работа с LinkedIn — полуавтомат (Этап 3)

**Feature Branch**: `003-linkedin-invites`

**Created**: 2026-07-13

**Status**: Draft

**Input**: User description: "Этап 3 PLAN.md §6: еженедельно — заготовки инвайтов для CTO/CPO/HRBP/Senior IT Recruiter по конфиг-списку компаний: people-search URL + персонализированный текст ≤300 знаков; статусы proposed→sent→accepted кнопками; напоминание о неотправленных. Автоматизации отправки/чтения LinkedIn НЕТ (grep-тест на отсутствие HTTP к linkedin.com). Eval: invite_rubric — LLM-as-judge (персонализация, длина, роль, без штампов) pass ≥0.9."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Еженедельный пакет заготовок инвайтов (Priority: P1)

Каждый понедельник владелец получает в Telegram пакет заготовок для нетворкинга: для каждой компании из его конфиг-списка и каждой целевой роли (CTO, CPO, HRBP, Senior IT Recruiter) — карточка с готовой ссылкой на people-search LinkedIn (люди этой роли в этой компании) и персонализированным текстом инвайта ≤300 знаков. Владелец открывает ссылку, находит человека, копирует текст, отправляет инвайт **сам** — система никогда не касается LinkedIn.

**Why this priority**: это продукт этапа; всё остальное (статусы, напоминания) — обвязка вокруг пакета.

**Independent Test**: команда `/invites` → приходит пакет заготовок по конфигу; каждая ссылка открывает корректный people-search; каждый текст ≤300 знаков, упоминает компанию и уместен для роли.

**Acceptance Scenarios**:

1. **Given** конфиг с 5 компаниями и 4 ролями, **When** еженедельный запуск (или `/invites`), **Then** приходит ≤20 заготовок; search_url корректно кодирует роль+компанию ([N-C1]).
2. **Given** текст инвайта от LLM длиннее 300 знаков, **When** валидация, **Then** реджект схемой → 1 retry → при повторной неудаче заготовка с шаблонным текстом (пакет не срывается) ([N-U2], N2).
3. **Given** заготовка уже создавалась для пары (компания, роль) и не отправлена, **When** новый запуск, **Then** дубликат не создаётся — показывается существующая.
4. **Given** DRY_RUN=true, **When** запуск, **Then** пакет помечен «ТЕСТ» (внешних действий у этапа нет по построению — N1).

### User Story 2 - Статусы заготовок кнопками (Priority: P1)

На каждой карточке-заготовке кнопки: «📤 Отправил» (proposed→sent) и «✅ Принял» (sent→accepted). Статусы движутся только вперёд; попытка «принял» до «отправил» отклоняется с подсказкой. Команда `/invites_status` показывает воронку нетворкинга (сколько proposed/sent/accepted).

**Why this priority**: без статусов невозможно ни напоминание (US3), ни измерение эффективности нетворкинга.

**Independent Test**: нажать «Отправил» → статус sent, кнопка меняется на «Принял»; нажать «Принял» → accepted; попытка обратного перехода — вежливый отказ ([N-U1]).

**Acceptance Scenarios**:

1. **Given** заготовка proposed, **When** «📤 Отправил», **Then** статус sent, время зафиксировано.
2. **Given** заготовка sent, **When** «✅ Принял», **Then** статус accepted (терминальный).
3. **Given** заготовка accepted, **When** любая кнопка, **Then** IllegalTransition — статус неизменен, ответ «уже финальный» ([N-U1], N3).
4. **Given** `/invites_status`, **Then** счётчики по статусам за всё время и за неделю.

### User Story 3 - Напоминание о неотправленных (Priority: P2)

Если с прошлого пакета остались заготовки в статусе proposed, владелец получает напоминание (вместе со следующим пакетом или в середине недели): «осталось N неотправленных инвайтов» со ссылкой-командой посмотреть их.

**Why this priority**: ценность нетворкинга — в регулярности; напоминание борется с прокрастинацией, но работает только поверх US1+US2.

**Independent Test**: оставить заготовку proposed → при следующем еженедельном запуске приходит блок «неотправленные: N».

**Acceptance Scenarios**:

1. **Given** 3 заготовки proposed старше 3 дней, **When** еженедельный запуск, **Then** в пакете блок-напоминание с количеством и командой `/invites_pending`.
2. **Given** все отправлены/приняты, **When** запуск, **Then** напоминания нет.

### Edge Cases

- LLM недоступен/ключа нет → заготовки с шаблонным текстом (роль+компания подставлены), пакет приходит; LLM_MODE=fake — детерминированный стаб (паттерн этапов 1–2).
- Компания с не-ASCII названием («Яндекс») → search_url корректно URL-кодируется ([N-C1]).
- Конфиг-список пуст → job success, сообщение «добавьте компании в конфиг», пакета нет.
- Персонализация без данных о человеке: текст персонализируется под РОЛЬ и КОМПАНИЮ (имени адресата у системы нет и быть не должно — N1); владелец дописывает имя при отправке.
- Инвайт-текст со штампами («I came across your profile») → ловится eval-рубрикой [N-E1], не кодом.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST еженедельно (конфиг, по умолчанию понедельник) формировать пакет InviteDraft по декартову произведению конфиг-списков компаний и ролей, без дубликатов к неотправленным существующим ([N-C1]).
- **FR-002**: Каждая заготовка MUST содержать: роль, компанию, people-search URL (корректное URL-кодирование, включая кириллицу) и персонализированный текст ≤300 знаков (упомянута компания, тон под роль, без штампов) — схема с лимитом, невалидно → 1 retry → шаблонный фолбэк ([N-U2], N2).
- **FR-003**: Система MUST NOT выполнять никаких HTTP-запросов к linkedin.com и поддоменам; гарантия — статический grep-тест по кодовой базе ([N-U3], N1). Единственное взаимодействие с LinkedIn — владелец руками по ссылке.
- **FR-004**: Статусы MUST двигаться только proposed→sent→accepted (кнопками); недопустимый переход → IllegalTransition, состояние неизменно ([N-U1], N3); заготовки персистятся (linkedin_target, DOMAIN.md §4).
- **FR-005**: MUST существовать напоминание о заготовках proposed старше порога (конфиг) и команды `/invites`, `/invites_pending`, `/invites_status`.
- **FR-006**: Генерация текстов MUST идти через LlmPort (llm_call, O1); промпт версионируется; LLM_MODE=fake даёт детерминированный стаб.
- **FR-007**: MUST существовать eval-контекст `invite_rubric`: LLM-as-judge по рубрике (персонализация: компания упомянута; роль адресата корректна; ≤300 знаков; нет штампов из стоп-списка) — pass rate ≥0.9 ([N-E1]); judge-модель из конфига.

### Key Entities

- **InviteDraft** (DOMAIN.md §3.5): title (роль адресата), company, search_url, invite_text, status ∈ {proposed, sent, accepted}, created_at, sent_at?, accepted_at?. Хранение — таблица linkedin_target (миграция 0004).
- **Конфиг нетворкинга**: списки компаний и ролей + расписание — env.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Понедельник → пакет ≤N_компаний×N_ролей заготовок; каждая ссылка открывает валидный people-search (acceptance PLAN.md).
- **SC-002**: Кейсы TEST_CASES.md раздела 4 ([N-U1]–[N-U3], [N-C1]) зелёные; grep-тест не находит HTTP к linkedin.com.
- **SC-003**: Статусы обновляются кнопками; обратные переходы невозможны (property-подход к N3).
- **SC-004**: `make eval CONTEXT=invite_rubric`: pass rate ≥0.9 ([N-E1]).
- **SC-005**: 🖐 Ручная проверка: владелец проверяет 5 заготовок и вручную отправляет первую партию.

## Assumptions

- Список компаний-целей составляет владелец (конфиг `LINKEDIN_COMPANIES`); стартовый список согласуется при первом прогоне; роли по умолчанию — CTO;CPO;HRBP;Senior IT Recruiter (PLAN.md §6).
- people-search URL строится шаблоном `https://www.linkedin.com/search/results/people/?keywords=<role>%20<company>` — это ссылка ДЛЯ владельца (открывает он сам), не HTTP-запрос системы; grep-тест проверяет отсутствие обращений кода, а не строк-шаблонов URL (уточнение [N-U3]).
- Модель генерации — `LLM_MODEL_SUMMARY` (Flash-Lite) до появления отдельной задачи; judge — `LLM_MODEL_JUDGE`; пока реальный LLM недоступен (OpenRouter), генерация — стаб, eval `invite_rubric` выполняется после подключения RU-агрегатора (хвост, аналогично этапам 1–2).
- Личных данных адресатов система не хранит и не запрашивает (только роль+компания) — соответствие N1 и минимизация ПД.
