# Research: Работа с LinkedIn (Этап 3)

## 1. people-search URL

- **Decision**: `https://www.linkedin.com/search/results/people/?keywords=<urlencode(role + " " + company)>` — самый устойчивый публичный формат поиска; кириллица кодируется percent-encoding ([N-C1]). Ссылка — данные для владельца, не запрос системы: [N-U3]-grep проверяет отсутствие HTTP-клиентских обращений к linkedin.com (httpx/requests с этим доменом), а не строковых шаблонов.
- **Alternatives**: фильтры company= по id (нужен lookup через API/скрейпинг — нарушает N1 — отвергнуто).

## 2. Grep-тест N-U3

- **Decision**: тест сканирует `app/` на паттерн `linkedin\.com` и падает, если вхождение находится вне белого списка (домен networking: шаблон search_url; домен correspondence: маршрутизация писем-уведомлений). Дополнительно: в `adapters/` не существует модуля linkedin-клиента. Это статическая гарантия «кода, который умеет ходить в LinkedIn, в принципе нет».

## 3. Дедуп заготовок

- **Decision**: уникальность по (company, title) среди НЕ-accepted: повторный еженедельный запуск не плодит дубликаты, пока владелец не отправил/не получил accept; после accepted пара снова доступна (можно попробовать другого человека той же роли через время). Индекс częściowy: unique (company, title) WHERE status != 'accepted'.

## 4. Стаб инвайт-текста (LLM_MODE=fake)

- **Decision**: детерминированный шаблон: «Здравствуйте! Я Engineering Manager (10+ лет, финтех/платформы). Слежу за {company} — интересно, как устроена инженерная культура. Буду рад связаться{role_tail}.» — ≤300 знаков, компания упомянута (проходит будущую рубрику). Тот же текст — фолбэк при недоступном реальном LLM (edge case спеки).

## 5. Расписание и напоминание

- **Decision**: cron `INVITES_CRON` (по умолчанию `0 11 * * 1` — понедельник 11:00 МСК, после утреннего дайджеста); напоминание о proposed старше `INVITES_REMIND_DAYS` (3) — блоком в том же пакете. Отдельного mid-week job'а не заводим (меньше движущихся частей; спека допускает «вместе со следующим пакетом»).

## 6. Eval invite_rubric ([N-E1])

- **Decision**: датасет — сгенерированные заготовки (append-only, реальные из прогонов); judge-промпт по рубрике: (1) компания упомянута, (2) тон уместен роли, (3) ≤300 знаков (проверяется и кодом), (4) нет штампов из стоп-списка конфига («came across your profile», «synergy», «взаимовыгодное сотрудничество»…). pass ≥0.9. Требует judge-модели → выполняется после подключения RU-агрегатора (хвост этапа, как eval этапов 1–2).
