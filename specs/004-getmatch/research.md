# Research: Работа с GetMatch (Этап 4)

> Дата исследования: 2026-08-12. Метод: чтение публичных страниц + прямые HTTP-пробы эндпоинтов getmatch.ru (без логина, без браузера). Живой вход в аккаунт владельца не выполнялся — авторизованные ветки помечены как открытые вопросы.

## 0. Отправная точка: почему не userbot

Исходный план (PLAN §6): userbot Telethon читает бота GetMatch в Telegram. **Заблокирован тем же барьером, что HH** (`specs/001-hh-digest/research.md`, «Пересмотр 2026-07-17»): my.telegram.org стабильно отдаёт `ERROR` при создании api_id (неустранимый баг на стороне Telegram, проверено на нескольких устройствах и IP VPS). Второй Telegram-аккаунт под userbot завести нельзя → канал недоступен. Владелец выбрал парсинг сайта getmatch.ru.

## 1. Доступ к данным: варианты и решение

**Что есть на getmatch.ru:**
- Публичный каталог вакансий — страницы `/vacancies`, `/catalog`, детальные `/vacancies/{id}-{slug}`.
- Телеграм-бот и авторизованный кабинет `/profile`, `/api/vacancies` (персональная подборка).

**Пробы (2026-08-12):**

| Проба | Результат |
|---|---|
| `GET /vacancies` (HTML) | HTTP 200, ~269 KB, `x-powered-by: Next.js`, `server: nginx`. В **сыром** HTML **0** карточек `/vacancies/{id}` — список рендерится на клиенте (app-router, `self.__next_f`). Скрейп HTML → нужен Playwright. |
| `GET /api/vacancies` | HTTP 401 `{"detail":"Login required"}` — персональный фид, требует авторизации. |
| `GET /api/offers` | **HTTP 200, `application/json`** — `{"meta":{"total":779,"offset":0,"limit":20},"offers":[…]}`. **Без логина.** Полные поля вакансии. |
| `GET /api/offers?limit=3&offset=100` | HTTP 200, пагинация `offset/limit` работает (`meta` отражает запрос). |
| Признаки анти-бота | Cloudflare/капчи не обнаружено; nginx + Next.js, обычный User-Agent проходит. |

- **Decision**: основной источник — **публичный JSON `GET https://getmatch.ru/api/offers`** через **httpx** (не Playwright). Отдаёт готовые структурированные поля, дедуп по `id`, вилка и HTML-описание — всё в JSON. Легче по ресурсам на порядок: никакого Chromium (см. §4 — снимает привязку к апгрейду железа).
- **Rationale**: чистый JSON → чистая функция-парсер + golden-diff (паттерн API-адаптеров проекта, ближе к сайтам-скрейперам этапа 5 с JSON-эндпоинтом, чем к Playwright-хвосту HH). HTML-страница `/vacancies` рендерится на клиенте — скрейп HTML потребовал бы браузер и не дал бы ничего сверх JSON.
- **Alternatives**:
  - Playwright по HTML `/vacancies` — тяжело (Chromium ~300–700 MiB, не влезает в текущий 1 GB, `docs/INFRA.md`), избыточно при наличии JSON — **отвергнуто**.
  - Авторизованный `/api/vacancies` (персональная подборка) — требует логина владельца (сессия/куки); даёт персонализацию, которая нам не нужна (релевантность считает наш RELEVANCE против резюме EM). Оставлен опциональным хвостом (§5), не в scope MVP.
  - userbot — заблокирован (§0).

## 2. robots.txt и ToS-соображения (открытый вопрос)

`GET /robots.txt` содержит среди прочего:
```
User-agent: *
Disallow: /api/
Disallow: /profile/
Disallow: /applications/
...
Sitemap: https://getmatch.ru/sitemap.xml
```

- **Факт**: `/api/` (включая `/api/offers`) закрыт для краулеров через robots.txt. HTML `/vacancies` — **не** в Disallow, но клиентский рендер делает его непригодным без браузера.
- **Позиция**: JobPilot — **персональный агент одного пользователя** (владельца), а не массовый краулер: 1 прогон/сутки, вежливый rate (1 rps), читает офферы, публично адресованные IT-кандидатам. Это отличается по природе от bulk-crawl, но **robots.txt формально запрещает `/api/`**. Правила проекта (PLAN §7, этап 5) требуют «честный User-Agent, robots.txt».
- **Decision**: не проектируем обход и не игнорируем факт молча. Источник **выключен по умолчанию**; включение — **только явным решением владельца** (`/approve_scraper getmatch`) по итогам canary (человек в контуре, constitution VI). Честный User-Agent, идентифицирующий владельца/агент, 1 rps. Если GetMatch начнёт отдавать блок/капчу — `SourceFetchFailed` + эскалация, **без обхода** (S5, constitution IV). Альтернатива при отказе владельца от `/api/` — Playwright по публичному HTML (гейтится железом) или скип этапа. Это зафиксированный открытый вопрос, эскалируется владельцу до боевого включения.

## 3. Структура offer и стабильность полей

Поля одного элемента `offers[]` (подтверждено на живом ответе):

| JSON-поле | Пример | Использование |
|---|---|---|
| `id` | `35226` | `external_id` (str) → SourceRef |
| `position` | `"Главный технический архитектор ИТ-продукта"` | `title` |
| `company.name` | `"Гринатом"` (может быть `null` при инкогнито) | `company` |
| `url` | `/vacancies/35226-glavnyi-...` | абсолютный `https://getmatch.ru{url}` |
| `salary_display_from` / `salary_display_to` | `300000` / `550000` (или `null`) | `Salary.from/to` |
| `salary_currency` | `"RUB"` / `null` | `Salary.currency` |
| `salary_hidden` | `true`/`false` (~70% `true` в выборке) | `true` → `Salary(None,None,None)` |
| `salary_taxes` | `"net"`/`"gross"` | в `raw` (не в доменной Salary) |
| `offer_description` | HTML (`<b>…</b>\n…`) | `description_raw` → очистка HTML (S3) |
| `skills_objects` | `[{name,slug,is_custom}]` (напр. Java, Kafka) | теги/стек → `raw`, опц. в текст скоринга |
| `location_items` | `[{label:"Москва", format:"remote", exclude}]` | локация → `raw`/description |
| `published_at` | ISO `2026-08-04T11:04:38` | диагностика/сортировка |
| `is_active` | `true`/`false` | `false` → offer пропускается |
| `offer_type` / `type` | `one_day_offer_v3` / `only_web` | в `raw` |

- **Пагинация**: `meta.total` (779 на дату), дефолт `limit=20`; листаем `offset += limit` до `offset ≥ total`. Верхний `limit` не проверялся на предел — берём консервативный (20–50), 1 rps.
- **Фильтры**: пробные `salary_from/grades/specializations` не меняли `meta.total` → серверных фильтров под эти имена нет. Тянем полный активный фид, фильтр EM-ключей и скоринг — на своей стороне (паттерн проекта).
- **Стабильность**: структура фиксируется golden'ом обезличенного ответа; изменение полей ловит golden-diff тест ([S-C0b]-аналог, [S-C6]).

## 4. Ресурсы и железо

httpx-запрос к JSON — десятки KB, парс в чистой функции, **без Chromium**. В отличие от этапа 5 (Playwright, +300–700 MiB, `docs/INFRA.md`), GetMatch-источник **исполняется на текущем VPS** (1 vCPU / ~1 GB, без swap) — деплой не гейтится апгрейдом железа. Это ключевой выигрыш JSON-пути над авторизованным HTML-парсингом.

## 5. Опциональный хвост: персональный фид (вне scope MVP)

`GET /api/vacancies` (401 без логина) — персональная подборка под резюме владельца. Подключение потребовало бы разовой авторизации владельца (сессия/куки, возможно headful-логин как `hh_login`) и хранения session-секрета. Не нужен для MVP (релевантность считаем сами) и добавляет ПД/секрет — **отложен**. Если публичный фид окажется беден/нерелевантен, вернуться сюда отдельной спекой.

## 6. Eval `getmatch_parse` ([S-E1])

- Датасет `eval/datasets/getmatch_parse/v1.jsonl`: `{"input": {<offer JSON>}, "expected": {title, company, url}}` из обезличенных реальных offers (append-only). Раннер прогоняет `parse_getmatch_offers` пооффер, метрика — доля точно извлечённых title/company/url; порог **≥0.95** (assertion, [S-E1]). Golden и датасет — один поток данных (обезличенный реальный ответ).

## 7. Вывод

Источник GetMatch **реалистичен и лёгкий**: публичный JSON-эндпоинт отдаёт полные поля вакансий без логина и без браузера, httpx-адаптер по паттерну проекта, исполняется на текущем железе. Единственный содержательный риск — **ToS/robots (`Disallow: /api/`)**: решается человеком в контуре (owner-approval после canary), обход не проектируется.
