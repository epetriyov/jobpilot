> Повод: при каждом деплое `kswapd0` уходит в 100% CPU, load доходил до **41** на одном
> ядре, сборка образов заканчивается OOM и роняет соседние проекты.

## 2. Диагноз: почему именно `kswapd0`

Свободно ~66 MiB, свопа нет. Когда сборка просит ещё 300–600 MiB:

1. Ядро уходит в агрессивный reclaim; `kswapd0` крутится на 100%, **пытаясь освободить то,
   чего освободить нельзя** — анонимную память некуда вытеснить (swap = 0).
2. На **единственном** ядре этот спин вытесняет всё остальное → load 20–40.
3. Дальше OOM-killer, деплой рвётся на середине (так и вышло: код обновился, а миграция
   `0004` не применилась).

То есть это не «медленный диск» и не утечка, а **дефицит RAM + отсутствие swap + 1 ядро**.

## 4. Требования к железу

### 4.1 Прод — текущий объём (JobPilot на email-источнике + билеты + сайт)

| | vCPU | RAM | Диск | swap |
|---|---|---|---|---|
| Минимум | 2 | **2 GB** | 40 GB SSD | 2 GB |
| **Рекомендуется** | **2** | **4 GB** | **60 GB SSD** | **2 GB** |

2 GB закрывают базу (0.75) + сборку (0.6) + разовые контейнеры с запасом. 4 GB дают
спокойный режим: деплой не конкурирует с рантаймом.

### 4.2 Прод — после этапа 5 (7 скрейперов, Playwright) и этапа 6 (pgvector, MCP)

| | vCPU | RAM | Диск |
|---|---|---|---|
| Минимум | 2 | 4 GB | 60 GB SSD |
| **Рекомендуется** | **4** | **8 GB** | **80 GB NVMe** |

Обоснование: база 0.75 + Chromium 0.6 + сборка 0.6 + индекс pgvector 0.5 ≈ **2.5 GB пик**;
8 GB оставляют место под рост БД и параллельные скрейпы. Chromium — CPU-жадный рендеринг,
на 1–2 ядрах скрейп будет конкурировать с ботом; 4 ядра снимают это.
Диск: образ с Chromium +1.5 GB, build-кэш уже 0.95 GB, плюс бэкапы.

### 4.3 Дев-машина (локальная разработка)

| | Ядра | RAM | Диск |
|---|---|---|---|
| Минимум | 4 | 8 GB | 20 GB свободных |
| **Рекомендуется** | **8** | **16 GB** | **50 GB свободных** |

Нужно под: Docker Desktop с полным compose (4 контейнера), `uv sync`, pytest, Playwright
с Chromium, локальные eval-прогоны. 8 GB хватает, но Docker Desktop + браузер + IDE на
8 GB уже тесно.

## 5. Что сделать **до** апгрейда (снимает боль без денег)

1. **Swap 2–4 GB — самое ценное одним действием.** Убирает спираль `kswapd0` и OOM:
   ```bash
   sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
   sudo mkswap /swapfile && sudo swapon /swapfile
   echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
   sudo sysctl -w vm.swappiness=10   # своп только под реальным давлением
   ```
2. **Собирать образы вне бокса.** У проекта уже есть GitHub Actions: собирать в CI →
   пушить в GHCR → на VPS только `docker pull` + `up -d`. Это убирает **самый крупный
   пик памяти** насовсем; VPS перестаёт быть машиной сборки.
3. **Проставить лимиты памяти в compose** — чтобы JobPilot не ронял сайт и билеты:
   ```yaml
   deploy:
     resources:
       limits:
         memory: 256M   # bot, worker
   ```
   Ориентиры: bot/worker 256M, db 256M, alloy 96M, watcher 64M, traefik 64M.
4. **Почистить диск:** `docker builder prune` (0.95 GB кэша) + `docker image prune`
   (180 MB висящих слоёв).
5. **Пересмотреть alloy на маленьком боксе:** 70 MiB и **18% единственного ядра** —
   дорого для телеметрии. Либо увеличить интервал сбора, либо снять с этого хоста.

## 6. Рекомендация

Целевая машина под текущий и ближайший объём — **2 vCPU / 4 GB / 60 GB SSD**; при запуске
этапа 5 со скрейперами переходить на **4 vCPU / 8 GB / 80 GB**.

Независимо от апгрейда — пункты 5.1 (swap) и 5.2 (сборка в CI) стоит сделать сразу:
они устраняют причину падений деплоя, а не симптом. Лимиты (5.3) обязательны, пока три
проекта делят один хост.
